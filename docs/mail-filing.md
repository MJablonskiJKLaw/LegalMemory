# Deliberate mail filing

The MCP filing tools accept an original MIME message and its decoded attachments into a user-selected matter. `resolve_mcp_identity` supplies identity; arguments cannot supply a principal or role. The destination must have an active project and an explicit editor/owner/admin grant (or an administrator identity). Any matching project deny wins, including for administrators. Read receipts separately require current read authorization for every filed version and the same project boundary.

`list_mail_filing_destinations` pages writable destinations. `begin_mail_filing` reserves a caller/matter/replay-key upload; repeated requests return its current offsets or committed receipt. `upload_mail_filing_chunk` accepts canonical base64, contiguous offsets, and identical retries, up to 256 KiB per chunk. All components are verified before publication. `commit_mail_filing` atomically commits the receipt, separate matter-bound documents/versions/source objects, and existing pipeline processing states. `cancel_mail_filing` removes only uncommitted staging. `read_mail_filing` returns a readable receipt; `authorized_mail_filings` accepts at most 200 candidate IDs and returns only readable association identifiers. Callers must page their complete candidate set; this request bound is not a complete-result limit.

The manifest records the exact original and attachment hashes/sizes, headers, capture/receive times, and provider locator. Imported provenance is descriptive and grants no access. A maximum of 101 parts, 64 MiB per part and 96 MiB total applies. SQL upload staging expires after 24 hours and is purged on the next begin operation. There are at most two pending uploads per caller and 64 globally; PostgreSQL serializes reservations with a transaction advisory lock. Cancellation and expiry remove staged bytes. Committed originals follow the appliance's independent retention policy; deleting or disconnecting a mail provider has no effect on them.

Identical bytes share content-addressed storage, while each filing has separate documents and matter permissions. No hash lookup tool exists. Classify/relate stages preserve the explicit association and cannot merge a filed original into a different matter. Conversion and indexing use the existing pipeline; the receipt says ingestion is queued, not that indexing succeeded.

The artifact store uses its existing fsync/content-addressed publication before the database transaction commits. A process/IO failure in that boundary can leave an unreferenced content-addressed artifact; retry reuses and verifies it. Upload staging and the database association remain atomic. This feature does not automatically unlink globally deduplicated artifacts after a failed SQL transaction, because another producer may have acquired them. Existing appliance artifact retention remains responsible for orphan cleanup. Live deployment, provider certification, and legal retention policy are outside this change.

Validation: `PYTHONPATH=src python -m pytest --noconftest tests/test_mail_filing.py -q` uses only temporary SQLite/artifact fixtures and no model/provider calls. The migration merges the three pre-existing heads and adds two tables; test coverage checks upgrade/downgrade columns and foreign keys.
